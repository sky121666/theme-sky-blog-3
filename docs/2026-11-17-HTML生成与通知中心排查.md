范围为本地 8090 / Halo 2.27.3、工作区主题 0.9.51。不提交、不推送、不发布。初始排查没有写入菜单数据；后续按用户要求将四个 Dock 菜单改为普通 SVG 图标，详见 [Dock 图标与文字对齐修复](2026-11-17-Dock图标与文字对齐修复.md)。未清除整站页面缓存。

## HTML 慢在哪里

测量使用匿名请求、完整 HTML、`Cache-Control: no-cache`；同时记录首字节、完整响应和输出分段，不以页面缓存命中代表 SSR 速度。缓存命中约 10–24 ms，无缓存完整响应约 280–400 ms。gzip 与 identity 耗时接近。数据库 TCP 建连与 MySQL greeting 的本机测量也不能解释约百毫秒的停顿。

模板分段把主要停顿定位到菜单数据读取，其次是桌面内容图标查找；首页另有小组件数据查询。主菜单与 Dock 菜单的公共 API、仓库计时又将范围收窄：

| 对照 | HTTP 完整响应 | `ExtensionStoreRepository.findByNameIn` 累计耗时增量 | 仓库计数增量 |
| --- | --- | --- | --- |
| 空对照，3 次 | — | 3.67–4.40 ms | 每次 2 |
| 主菜单，2 次，约 11.3 KB | 13.98–14.70 ms | 8.45–10.29 ms | 每次 4 |
| Dock 菜单，2 次，约 1.33 MB | 144.00–149.16 ms | 134.32–144.62 ms | 每次 4 |

同样的读取次数，Dock 数据显著更大、更慢。三个 `metadata.annotations.image_url` 存放了 Base64 PNG，总计 1,324,294 字符，占这组 Dock 菜单四项原始 JSON 的 99.54%。Halo 读取完整扩展对象后再解析 metadata；模板不输出这些图片，仍然会承担它们的读取成本。因此这不是给 Swup 再加动画或预取就能消除的根因。

仓库计时是进程级累计值，使用交错空对照评估背景读请求；不能把全部耗时继续细分为 MySQL 执行、驱动接收或反序列化。本轮没有测数据库物理执行计划，也没有宣称扫描了整张表。

### 流式输出中的等待段

为区分“首批数据已到”与“服务端仍在生成”，又记录同一组请求的流式数据块及页面标记。四类页面都在约 24 KiB 处出现最大的后段等待，完整响应通常由三个主要阶段组成：最初约 24 KiB、约 32–82 KiB 的主题壳层和注入资源、约 82 KiB 之后的页面主体与协议数据。

以最终页面片段核对，24–82 KiB 附近包含 `plugin-bytemd` 注入的 Mermaid 主题 CSS、主题启动资源、插件页头和通知中心模板；页面主体在通知中心模板之后才出现。该段大约贡献 140–230 ms 的连续等待，首页首页组件段另有约 40–50 ms。主题模板里的通知中心 markup 只约 2.3 KiB，不能把这段全部归因于它的模板体量；插件样式、主题壳层组装、Servlet 流式缓冲和服务端数据读取都可能参与，现有测量还不能把每个毫秒继续细分到具体组件。

因此不能只用“首个字节时间短”证明页面快：首批数据到达后，文档正文和窗口可达仍需等待后面的主体；也不能把所有约 300 ms 都归到 Dock 菜单。Dock 菜单大图是已经确认且可修复的主要独立成本，24–82 KiB 壳层段则是下一项可测量的结构成本。当前没有为此缓存整段 HTML 或改变输出顺序，避免把一次缓存命中当成 SSR 改善。

流式证据：`output/html-ssr-20261117/final-gaps.json`、`output/html-ssr-20261117/final-gaps.log`。

## 通知中心首开折返

12 张卡片的布局宽高、网格列宽均稳定。变形来自首开动效：内联动画起点先触发 CSS transition，使卡片从终点向起点移动；随后 Web Animations 再让卡片回到终点。旧版实测横移为 `0 → 3.70 → 9 → 0.25 → 0 px`，透明度为 `1 → 0.91 → 0.44 → 0.98 → 1`。

修复让入场动画从延迟阶段接管首帧，不再写触发反向 CSS transition 的内联起点。独立审查另补出关闭末段重开的问题：卡片先于面板结束，原逻辑忽略仍保持关闭终态的已完成动画，重开时透明度会从 0.18 跳到 1。现在将这些动画纳入反向接管，已完全展开的卡片仍通过最终状态判断免于重播。

保留卡片交错、面板开关反转、减少动态效果及关闭时零卡片的惰性挂载。两处回归均先复现原问题再验证修复，动效与桌面专项 **40/40** 通过，包含原生 Chromium 的 CSS+WAAPI 首帧和关闭末段重开测试。

## 文档“将目录钉住”：已定位并修复

用户通过 `/docs/halo-theme-sky-blog-1` 的截图明确指出右侧「本页目录」标题栏按钮。之前围绕无章节标题的 `/docs/halo-theme-sky-blog-1/1` 排查并写下“尚未定位”，没有对应用户指向的页面和控件，这一结论已更正。

真实页面复现：该按钮使用 `panel-right-close` 图标，与工具栏共用 `data-docsme-toggle-toc`，点击只会收起目录，没有固定状态。窗口内容宽度为 958px 时，右侧目录按旧的 1080px 断点变成覆盖正文的浮层，因此收起/展开回归通过并不代表固定功能可用。

修复将「固定」与「关闭」分为独立按钮：

- 固定时右侧占独立的 220px 列，不覆盖正文；正文和目录列表分别滚动，目录标题栏保持不动。
- 点击正文、选择本页章节都不关闭已固定的目录；关闭后仍可从工具栏按原固定模式重新打开。
- 取消固定后保持浮层展开，可点外部、关闭按钮或 Esc 收起，键盘焦点返回工具栏。
- 固定偏好保存在当前标签页的 `sessionStorage`，Swup 更换文档和浏览器返回均会恢复。窗口内容不足 920px 时暂用浮层并隐藏固定按钮，恢复宽度后沿用偏好；默认仍在宽于 1080px 的窗口显示固定列。
- 无标题文档不显示空目录；固定偏好的存储失败不会阻止本地交互。

专项先验证真实模板缺少固定入口的失败，再验证固定/收起、独立列几何、正文与目录滚动、窄窗口回退和重新挂载。该轮构建 `0.9.51 / 498d777544ca` 已通过构建、架构检查、App 协议检查、目录专项与 8090 重载。8090 的文档体验专项在 1440、1024、390、320 四种浏览器宽度通过 24/24 项，包含 Swup 切换、浏览器返回及手机目录操作；主题相关运行错误为 0。固定后的真实 958px 窗口保留约 383px 正文宽度；此项阅读空间不足，后续修复如下。
