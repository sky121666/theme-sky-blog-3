# 冷启动：点开一篇文章，什么时候真正能读？

对象是 8090 的开发站，Halo 2.27.3、Sky Blog 3 0.9.51，最终资源版本 `3baf195b4b53`。同一次访问有三个不同的时刻：HTML 收完、阅读窗口露出、主题和导航脚本就绪。出现壁纸、开机画面或者已经收到 HTTP 200，都不能说明读者已经看到标题。

## 阅读入口

- 直达文章或文档章节：服务端输出可见的窗口和正文。桌面尺寸下先用阅读页自己的 CSS 定位，窄屏继续全屏。只要 HTML 和样式可用，关闭 JavaScript 也能滚动。开启 JavaScript 时，窗口管理器照常接管，应用已记住的尺寸和位置。这两种直达入口不播放挡住正文的开机遮罩；首页保留原先的体验。
- 打开别的窗口再后退：文章使用窗口的滚动位置，Docsme 使用正文阅读区的滚动位置。侧栏和阅读区独立滚动；记录外层窗口会让章节返回顶部。
- [规范地址](功能/Docsme/规范地址.md)：SEO 工具集启用时使用插件的输出；未启用时使用主题根据 Docsme 数据生成的地址。项目入口可以随默认章节变化，不需要重定向。

## 怎样测「无缓存」

使用新的 Chromium 上下文，关闭浏览器 HTTP 缓存、阻止 service worker，对 8090 请求发送精确的 `Cache-Control: no-cache`，并检查 HTML 响应没有页面缓存的 `X-Halo-Cache-At`。普通 GET 单独采样。这里不重启 Halo 和数据库，不清空整站缓存；“无缓存”不代表重启后的第一次数据库查询。[Chrome 网络面板的缓存与网络模拟说明](https://developer.chrome.com/docs/devtools/network/reference/#disable-cache)

常速测试包括七个入口的 HTTP、五个入口的浏览器直达，以及资料库→项目、归档→文章的实际点击。章节另测 80 ms 模拟延迟、10 Mbit/s 下行、CPU 四倍降速，及两者同时启用；每组取三次中位数，不能代表线上长尾或所有手机。会员使用普通开发测试账号，阻止外站请求，不能把与访客间的全部差异归因于登录。

同一章节，毫秒，自开始导航计时。修复前后「窗口露出」使用相同的遮挡检测；修复后另检查**章节标题本身**能被屏幕坐标命中。「交互就绪」是窗口露出、主题初始化完成且导航已挂载的首帧；不代表页面上每一个插件都加载完。

| 条件 | 修复前窗口露出 | 修复后窗口露出 | 修复后标题可见 | 修复后交互就绪 |
| --- | ---: | ---: | ---: | ---: |
| 本机访客 | 693 | 328 | 334 | 500 |
| 模拟 80 ms、10 Mbit/s | 2,168 | 622 | 623 | 2,040 |
| CPU 四倍降速 | 1,320 | 311 | 450 | 1,194 |
| 慢网络 + 慢 CPU | 2,241 | 763 | 764 | 2,162 |
| 登录开发会员（仅同源） | 685 | 308 | 332 | 502 |

另一组七个公开入口的 21 次无缓存请求全部绕过 Halo 页面缓存，完整 HTML 用时 227–305 ms；21 次普通 GET 命中页面缓存，用时 2–5 ms。桌面已打开后，资料库→文档项目的三次真实切换中位数为 303 ms，归档→文章为 340 ms；从目标 HTML 收完到目标就绪只用 38–45 ms。这里没有重现[早前一次九秒的等待](2026-11-17-窗口响应与交互修复.md)，也不能据此排除其他时段的慢请求。

## 桌面为何保留了，打开窗口仍然要等

1. **窗口没有刷新，但目标响应仍是整页。** 同一测试文档的无缓存 HTML 为 175,187 B，其中 `#window-frame-root` 为 24,318 B；文章分别为 176,974 B 和 24,492 B（匿名、未压缩，包含原始模板空白）。Swup 收到整页后取窗口、更新必要的页面信息，原桌面 DOM 不变。不能把差值全部视为浪费：head、SEO 与插件信息仍需同步；也不能从字节数推算数据库用时。完整响应同时让独立网址和浏览器直达工作。[Swup 的用途与导航生命周期](https://swup.js.org/getting-started/)
2. **首次显示曾错误地依赖整个桌面启动。** 同一修复前构建，只向新标签页写入“开机动画已播过”标志，其余缓存仍全关，章节窗口露出的中位数从 693 ms 变为 267 ms。再看 HTML，分别为 281 ms 和 246 ms：两组并非完全相同，但这几十毫秒的差距不能解释全部视觉等待。关闭遮罩能改善阅读，不会免掉下载和执行。
3. **首访还承担全局界面的成本。** 常速访客章节在交互就绪前完成约 1.34 MB 同源资源传输，不含 HTML；各组中位数为插件约 792 KB、主题约 398 KB、其余约 146 KB。实际下载较大的包括评论组件约 259 KB、AI 助手模块约 200 KB。公共 head 还有豆瓣、公式、受限阅读、Steam、超链接卡片五个非 defer/async 的插件脚本。这里能定位下载对象，不能把持续时间全部归给某一个插件。登录版同一章节 HTML 为 327,933 B，访客为 175,187 B；只有登录版带设置面板。
4. **图库与商城有不同的图片问题。** 本机常速、无缓存时，图库就绪前完成约 10.72 MB 同源资源传输。一张 WebP 就占 9.19 MB；其 400w / 800w / 1200w 候选实际是同一个上传地址，懒加载只改变请求时机。商城商品列表约 4.03 MB，但抽查商品图发现缩放确实生效：同一张 PNG 原图为 1586×992、2.93 MB，`?width=400` 为 400×250、292 KB，`?width=800` 为 800×500、1.13 MB。不能把商城也诊断成忽略宽度参数；应检查卡片实际显示宽度、图片格式和选图规则。这两个入口没有在慢网下另测，不从字节数推算加载时间。

## 后续优先级

1. **图库先取得真正的预览图。** 在有／无封面、动态图片和原图回退的样本上验证列表传输体积，再确认打开详情仍能看原图。商城另查小卡、列表和大卡的显示宽度，不一刀切降低详情图清晰度。
2. **阅读页缩短初始化链。** 先查评论和 AI 助手是否有官方按路由或按需加载入口，并核对受限内容、公式、评论发帖等真实功能。登录用户的设置编辑器可单独试验「打开设置时才加载」，验收包括首次打开、保存与恢复。页面仍然直接输出可读 HTML。
3. **整页导航只在数据支持时改。** 在仍由 HTML 响应主导的站内导航试验窗口片段：保留完整独立 URL，验证标题、规范地址、权限、历史和失败回退。预加载适合有导航意图的公开链接，帮助第二步点击；不会缩短第一次直接打开分享链接时的下载。没有证据支持为解决这批等待而替换 Swup 或添加新的动画库。

## 复测入口

本轮 `pnpm run check` 通过，`verify:reload` 的 13 个检查点通过。阅读专项 11/11：包括 1440 / 390 px 下关闭 JS 后滚动、桌面恢复保存的 1000×680 窗口、文档和文章后退均从 700 px 回到 700 px，以及插件规范地址在原始 HTML、初始化和 Swup 切换后保持一致。无 SEO 工具集及插件关闭 canonical 的分支通过离线契约验证；没有停用 8090 的插件。

导航矩阵桌面 20/20、手机 20/20。另行运行的全站浏览器 smoke 是**非零退出**：24 项中 22 项仅因同一外站 favicon 被浏览器拒绝（`ERR_BLOCKED_BY_ORB`），认证页返回 200、非法页码用例按预期返回 404，记录的页面和控制台错误为 0。没有把这些失败改成通过。

```sh
node scripts/verify-reading-entry-live.mjs
node scripts/measure-reading-cold.mjs
COLD_MODE=profiles COLD_OUTPUT=output/reading-profiles node scripts/measure-reading-cold.mjs
```

报告保存在本机的 `output/`，不随主题安装包分发。文章、章节或项目样本发生变化时，通过脚本的 `READING_ARTICLE_PATH`、`READING_CHAPTER_PATH`、`READING_PROJECT_PATH` 指定实际的公开内容。
