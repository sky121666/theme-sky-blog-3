## 流程与命令影响

| 动作 | 当前机制 | 影响 |
| --- | --- | --- |
| 推送 `main` | 同步 Git 代码 | 不自动运行 CI，也不创建 Release |
| 手动 CI | [ci.yaml](../.github/workflows/ci.yaml) 的 `workflow_dispatch` | 冻结安装、安装 Chromium、运行 `check`；配置 `SMOKE_BASE_URL` 时另跑真页 smoke |
| 本地构建与打包 | `pnpm run build`；已有当前源码对应资源可用 `pnpm run package` | 打包前核对构建身份；生成 ZIP，写入第三方声明后逐项核对运行文件；`build` 还更新 `templates/assets/**` |
| 主题 reload | `pnpm run verify:reload` | 使用本地 PAT 向 Halo 发送 reload 请求；需对应环境操作授权 |
| 依赖漏洞审计 | `pnpm run audit:security` | 向 npm 官方漏洞接口发送依赖树，需明确授权 |
| 公开 GitHub Release | [cd.yaml](../.github/workflows/cd.yaml) 的 `release.published` | 调用 `halo-sigs/reusable-workflows/.github/workflows/theme-cd.yaml@v5`，打包、上传 Release 制品并同步应用市场 |

本地提交、推送、标签和公开发布各有独立范围。已有授权覆盖时沿用；版本准备不能扩大为实际发布。CI 通过时仍需看真页步骤是否跳过。

## 发布前准备

1. 确定新版本及目标 Halo／插件组合，并保留上一稳定 ZIP 和主题配置备份。
2. 在同一候选状态同步 `package.json`、`theme.yaml`、[发布说明](发布说明.md)、对应文档及生成资源。发布后的改动应提高版本，不覆盖既有 Release。
3. 使用项目指定 Node 与 pnpm，冻结安装并完成适用门禁。安装或构建后的改动须重新检查对应资源和构建身份。
4. 处理全站验收阻塞：先确认活动主题、访问策略和测试账号授权。登录重定向、缺样本和插件页面跳过均需记录，不可改访问策略来绕过门禁。
5. 实际发布时再核对仓库 Secret `HALO_PAT` 具备目标应用的“版本管理”权限，以及主题和 CD 的 App ID 一致。当前配置为 `app-gqnoxtpt`，无需输出 PAT。

### 安装包内容与体积要求

- 正式 ZIP 按明确的分发范围打包，保留主题运行、版本声明、许可和发布展示所需文件。本地 DEMO 与测试专用素材、测试数据、调试截图和日志保留开发用途，通过打包规则排除，不进入正式安装包。
- `templates/assets/**` 只承载主题运行资源。商城 DEMO 原图归档到 `docs/商城/演示素材/`，测试 fixture 图片归档到 `scripts/fixtures/images/`；`docs/**`、`scripts/**` 按开发目录排除。旧 `templates/assets/images/shop-demo` 目录及其后代继续禁止进入正式 ZIP。新增开发素材目录时，同步维护打包 CLI 补丁中的 `ignorePatterns` 与发布包脚本的禁止路径检查，不能仅在某次打包时临时删除文件。
- 本轮本地 DEMO 商品图片已迁移到 Halo 附件，商品引用回读和页面验证见[第一批逻辑修复](2026-10-10-第一批逻辑修复.md)。后续样本仍分别记录目录归档、引用迁移和页面可访问性，不能只从仓库素材整理推导迁移成功。
- 常规 `pnpm run package` 先拒绝过期构建，再生成 ZIP；finalizer 在写入声明前再次核对构建身份。`pnpm run build` 先生成资源，再走同一打包链路。包校验逐项核对主题配置和全部 `templates/**` 运行文件，缺失、额外或字节不一致均失败，覆盖入口资源、共享 chunks、生成片段及静态图片。校验外部 ZIP 时使用对应版本的源码和生成资源，避免拿当前工作区验证历史版本。
- 发布前仍需复核该候选 ZIP 的实际条目、必需文件、版本和许可证，记录条目数、字节大小及 SHA-256。`pnpm run verify:release-package:tests` 在临时目录验证旧源码、缺失／篡改／额外资源和开发素材等反例，已纳入 `check`；不上传或部署测试包。
- 与上一正式 ZIP 比较体积；异常增长需按新增条目定位原因并在版本准备记录中说明。历史包和本地诊断包只作比较证据，不设未经验证的体积硬阈值。
- 现行 v5 CD 通过项目 `build` / `package` 调用 finalizer；每次发布均需确认对应日志中的发布包校验结果。发布后必须下载正式 ZIP 再校验，候选包的条目数、大小和摘要不自动等于 CD 制品。

### 验证命令

下面是候选版本的验证顺序，命令作用与样本范围详见[验证矩阵](验证与审计矩阵.md)。包校验必须显式传入 ZIP 路径；先将下面的 `<version>` 替换为已确定的候选版本。文档维护不需要执行整套流程。

`check` 必须先运行 `build-only`，再完成类型检查、契约与离线测试、资源预算和构建 smoke；读取生成资源的检查使用本轮产物。完整检查后使用 `package` 打包同一候选资源，避免在包校验前重新构建而改变验收对象。该顺序是执行要求，是否通过以本轮日志为准。

```bash
pnpm install --frozen-lockfile
pnpm run check
pnpm run audit:licenses
pnpm run package
pnpm run verify:release-package "dist/theme-sky-blog-3-<version>.zip"
pnpm run verify:reload
SMOKE_BASE_URL=http://localhost:8090 pnpm run smoke:playwright
PERF_BASE_URL=http://localhost:8090 pnpm run verify:performance
SMOKE_BASE_URL=http://localhost:8090 pnpm run verify:pjax-lifecycle
```

经明确授权另执行 `pnpm run audit:security`，记录生产和完整依赖图的结果。其联网和数据提交影响见[开发约束](开发约束.md)。

发布包校验由[verify-release-package.mjs](../scripts/verify-release-package.mjs)完成：检查包名、版本、可选 `RELEASE_TAG`、路径、禁止开发素材目录、必要许可证文件及嵌入文件一致性，输出条目数、字节大小和 SHA-256。本地 `package` / `build` 已自动调用该脚本，显式命令可用于独立复核指定 ZIP。它不验证站点的所有交互。最终构建资源、ZIP、Git 提交与测试报告应对应同一候选状态。

## 发布与发布后核验

在已经授权版本发布且门禁通过后：

1. 对已核对的提交创建精确版本标签，推送该标签并公开同版本 GitHub Release；不推送所有标签。
2. 由现有 CD 上传主题 ZIP 并同步 Halo 应用市场，无需另起手工制品流程。
3. 核对 Release 标签、标题、说明和 ZIP 版本一致；CD 的打包、Release 制品和应用市场任务均成功。
4. 下载正式 Release ZIP，按该版本校验包名、内容、许可证、开发素材排除、字节大小和摘要，并与上一正式 ZIP 比较；本地候选包结果不自动等于 CD 包结果。
5. 核对应用市场版本与最低 Halo 要求，保留上一稳定包和配置备份。

不要覆盖或改写已公开版本。发布失败时记录精确版本、CD 任务和外部状态，再决定是否重试。

## 失败恢复与回滚

- **主题运行回归：**在有站点操作授权时恢复上一稳定 ZIP，按相应备份恢复需要的主题配置，再复查核心页面及启用插件。更换主题包不会自动撤销已保存配置或插件数据。
- **源码回退：**保留公开 Git 历史，以正常撤销提交恢复对应源码、页面协议和生成资源；导航改动需同时检查守卫、入口及消费者，见[导航恢复说明](主题导航契约.md#验证与恢复)。
- **配置或业务写入：**按操作对象的备份恢复，并复查结果；附件上传、插件写入和账号操作有各自恢复范围，不能以代码回退替代。
- **发布失败：**先核对 GitHub 和应用市场是否已部分成功；不删除公开标签、Release 或市场版本，不自动开启额外恢复工作流。

官方操作参考：[Halo 应用发布](https://docs.halo.run/developer-guide/app-store/publish-app)、[GitHub Release 管理](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository)。
