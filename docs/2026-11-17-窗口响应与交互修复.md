# 窗口响应与交互修复

这次在本地 Halo 2.27.3、主题 0.9.51 上，把两个时间分开检查：**点击后何时有反馈**，以及**什么时候能操作真实内容**。原构建一次文档切换在 3 ms 就接受了点击，HTML 在 9,176 ms 收完，文档在 9,249 ms 就绪。改动画无法省掉其中九秒的等待。

## 为什么慢

- 桌面模板为每个分类、标签、文章和单页图标重复调用 Finder（Halo 的内容查询接口）来判断并输出标题、地址。现在同一轮、同一图标只查一次；修复前后 10 个实站图标输出的名称、链接与次序摘要一致。
- 普通公开页面也会服务端渲染系统设置编辑表单和素材选择器。访客原本就只能得到登录提示。这次保留其入口和权限协议，但不发送无法打开的表单；登录状态仍由 Halo 判断。在桌面上打开设置之前，也不再下载负责设置预览和恢复的 JS。
- Swup 必须收完并校验可以挂载的文档才能换正文。应用首页的等待原本只反映在链接上；另一方面，过期缓存、不可复用的响应、预取分包尚未到达，会产生不同的等待，不能都叫“动画慢”。允许共享的在途 GET 可以交给当前点击；`no-store` 已完成后不可留作下一次导航。不以扩大缓存权限换取快的测试数字。

## 8090 实测

对照构建为 `f5dcfee9bf1d → b6133802549a`，版本号均为 0.9.51。同一台机器、同一数据、桌面 Chromium、绕过页面缓存，每条路径各三次；浏览器计时从真实点击到目标应用发出 ready。小样本中服务负载有波动，不代表线上耗时分位数。

| 操作 | 修改前中位数 | 最终构建中位数 | 最终三次 |
| --- | ---: | ---: | --- |
| 文档首页 → 项目 | 6.355 秒 | 0.371 秒 | 2.293 / 0.371 / 0.370 秒 |
| 归档 → 同一篇文章 | 7.054 秒 | 0.868 秒 | 1.130 / 0.868 / 0.537 秒 |

最终六次浏览器操作，HTML 收完到应用就绪为 39–43 ms。单独请求归档，未压缩 HTML 从 331,890 B 降到 180,221 B；三次完整响应中位数从 6.363 秒到 2.123 秒。浏览器与直接请求是两组独立样本，不能相减作为数据库用时。普通首页的最后一次请求仍用了 3.459 秒，不能据此声称所有页面已秒开。

真实 Dock 与受控入口的 13 项开窗场景全部通过：发出导航接受事件后，预览节点在 16–43 ms 内插入，截图与几何断言另证其可见、位置正确；此数不是显示器首帧测量。瞬间曾因应用覆盖定位而把 `x=440` 画到 `x=880`；文档曾在恢复旧尺寸时从 850 px 跳到 960 px。前者移除应用的重复定位，后者让预览和正式窗口共同约束恢复尺寸。

完整构建检查、13 个重载检查点、桌面/手机各 20 个导航场景通过。独立的全站 smoke 共 24 项：19 项正常、1 项预期 404、4 项记录同一外站 favicon 被 Chromium 拒绝；页面脚本异常和控制台错误均为 0。所有计时、浏览器记录和截图在本地 `output/repair-audit-20261117/`，不进入发布包。

## 桌面动效怎样工作

| 用户操作 | 立即反馈 | 数据返回后 |
| --- | --- | --- |
| 从桌面进入受支持的公开应用首页 | 与请求并行显示该应用的窗口，沿用已记住的尺寸或正式窗口的初始位置。足够快时不闪占位窗口。 | 同位置显示真实内容，不再等动画完成；失败留在桌面，可以重试或打开另一项。 |
| 在窗口里读下一章、看详情或筛选 | 保留原窗口、当前内容及键盘焦点。 | 只更新目标区域；失败不丢原章节、列表或草稿。 |
| 手机、浏览器后退、登录或交易 | 沿用原有页面交互与业务状态。 | 登录、付款、加购等是否成功由实际响应判断。 |

初版开窗仅匹配桌面上的公开入口：文档、图库、友链、瞬间、豆瓣、Steam、追番、装备、商店首页和站点配置的归档首页；外链、带操作参数的链接、结算和支付不在此范围。快速连点按最后一次被接受的导航清理；减少动态效果时静态展示。开窗用浏览器原生 Web Animations API 的透明度、4 px 位移与轻微缩放，160 ms，取消不会阻塞导航。

Amicro 的 [Scale In 示例](https://github.com/Subhan-code/Amicro--Micro-transitions-/blob/73a6d5c2b28b30ad6f6d98550bb6175cbf51132b/registry/ui/scale-in.json)提供的是基于 React 与 Motion 的视觉组件。这里取其动作设计，不引入第二个渲染框架或路由器。Swup 仍负责 GET、预加载、历史和提交；主题按实际导航事件绘制窗口。

## 对现有架构的判断

桌面、Dock 和窗口状态需要长驻，而文章、章节和商品信息经常更换。当前的矛盾是：**浏览器只替换窗口，服务端却按完整页面提供数据。** 完整页面依然有价值：新标签直接打开、刷新、搜索引擎和没有脚本的访问都需要它。不合理的是同一窗口翻到相邻章节时也重复付这笔成本。

- **保留 Halo 模板与现有局部组件。** 现有样本中，HTML 到达后到可用是几十毫秒量级；还没有证据把几秒的等待归咎于 Alpine 与 Svelte 共存。两者可按区域分工，但一个节点只应由一个组件负责挂载与销毁。
- **明确只有一个导航决策者。** 当前主题禁用了 Swup 的自动链接、自动接管后退和默认动画；桌面协调器处理草稿、历史、原生登录交接与窗口提交，Swup 提供请求和预取。接回第二套自动监听会增加重复切换、重复历史和草稿丢失的风险。[Swup 官方生命周期](https://swup.js.org/lifecycle/)
- **有条件地试一种更轻的窗口响应。** 第一候选是公开 Docsme 章节。保留原始直达地址，只在插件或主题能区分并正确缓存两种表示时，让窗口导航接收正文、标题、规范地址、应用标识及挂载所需信息。沿用现有窗口要比先发送整张桌面再丢弃更有意义。实测冷请求、已预取点击、前进后退与离线失败；若没有稳定收益，或导致一次点击变成多轮串行 GET，就保留现状。这是下一阶段的候选方案，本轮没有新增接口。
- **拖动与滚动另行定位。** 网络时序能解释换页等候，不能证明 GPU 掉帧。真机拖动窗口、滚图库或让多个玻璃面板重叠时，应比较相同场景的帧时间，再决定是否减少背景模糊；不因看见 `backdrop-filter` 就删掉 macOS 视觉。

## 本轮功能回归

| 流程 | 关注的反例 |
| --- | --- |
| 瞬间、评论和点赞 | 发布结果不确定时同稿同名核对；不误删可能已引用的附件；手动离页能够保留未发送评论。 |
| 商城 | 优惠写入成功后只重读结算；删除回执与回读冲突时不能误结算；被拒的数量回到服务端值；不重复订阅加购；地区语言回退。 |
| 导航与阅读 | 可选预取分包不阻塞点击；无效或不完整 HTML 不提交；退出原生导航后仍可点击；重定向回原址不多写历史；文章点赞成功失效旧缓存，登录 HTML 不当作点赞成功。 |
| 其余内容界面 | 归档与图库半截分页保留原列表并可重试；手机文档失败保留侧栏和焦点；友链后退回到原卡片；Steam 日期不可用与确定无记录分开；豆瓣缺封面或地址有正确回退；手机图库右侧评论表单使用实色表面。 |

复跑时使用同一开发站 `http://localhost:8090`，先构建，再重载。用 `scripts/verify-desktop-launch-live.mjs` 暂扣 GET 来观察桌面开窗；用 `scripts/verify-content-recovery-live.mjs` 操作列表、预览与失败后重试；用 `pnpm run verify:navigation:pages` 运行公开页面矩阵。写入异常使用浏览器拦截的受控回执，不用真实的订单、附件或评论制造错误。普通站点缓存与 `no-cache` 的时间须分别记录；旧页面返回得再快，也不算验收到新版本。
